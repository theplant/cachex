# 同一个进程里，读到的值尽量不倒退

写入顺序守卫（[ADR 0003](0003-striped-backfill-guard.md)）只挡住 `Cache` 自己的写入。数据源被绕过 `Cache` 修改、只靠 TTL 更新时，两次回填之间还会乱序，读者先读到新值、再读到旧值：

- **复制和刷新撞上**：第一层没有、第二层陈旧时，读取把第二层的 v1 复制上来；刚读完还没回填，刷新就把数据源的 v2 写进两层；复制随后落地，第一层回到 v1。
- **两次问数据源重叠**：刷新正在问数据源，普通读取又问了一次，先返回的那次读到了更新的值，后返回的旧值又写了回去。原来的 `WithFetchesPerKey(n)` 让同一个 key 的 n 次读取回源也能这样重叠（已删除，见 [ADR 0021](0021-one-fetch-per-key.md)）。

我们做了两件事：

1. **回填之间按分片排队，从下层复制的条目不覆盖更新的答案**：回填拿到分片读锁、核对完写入代数之后，再拿分片的回填锁；复制上来的条目先读一次目标层，目标层的条目 `CachedAt` 更晚就不写这一层。打开了租约的层不用读，只有持有租约的回源能写它。
2. **同一个 key 同时只问一次数据源**：问数据源之前在 `sourcing` 里登记；已经有别的回源在问，就等它的结果，不再问。登记在回填之后才注销，写入摘除它。

两件合起来，数据源的回答按顺序落下，复制又不会盖过它们。常见的乱序就此消除，但只靠 TTL 时这是**尽力而为**，不是保证，见下文「收窄」。

## 考虑过的方案

- **不回填下层的陈旧条目**：消除第一种，但第一层会在条目陈旧的整段时间里空着，每次读都去下层；数据源宕机、刷新一直失败时尤其明显。也不解决第二种。
- **复制上来的条目马上腐烂**：没用，问题是覆盖，不是寿命。
- **数据源的回答也做比较**：同一个 key 同时只问一次之后，没有更新的回答会在它之前落下，读这一次是白花的。
- **只做比较、不合并问数据源**：两次重叠的回答排不出先后：按回答时间，后返回的旧值会赢；按开始时间，先开始、后读到新值的会输。没有数据源的版本号，只能不让它们重叠。
- **比较时在后端里原子地「比较后写入」**：每个后端都要多一个原子操作（Redis 要 Lua、表要条件更新）。进程内排队之后，比较和写入之间不会再有别的回填插进来，用不着。

## 后果

- 未命中多一次登记（`sync.Map`，3 次分配）；纯内存的未命中基准约慢 15%，真实的未命中还要加上数据源的往返。
- 「上层未命中、下层命中」的复制多读一次上层（通常是内存层）。
- 回填之间会互相等（同一个分片），但从不等写入；批量回填按分片编号拿回填锁，不会死锁。
- 每个分片多 8 字节，一个 `Cache` 多 32 KB。
- 其他实例的写入经共享层到达这个实例的内存层时，没有这个顺序保证；那要靠失效广播（见 [ADR 0023](0023-invalidation-broadcast.md)）。

## 收窄（2026-10-14）

这条决策承诺过「同一个进程里读到的值不倒退」，包括数据源被绕过 `Cache` 修改、只靠 TTL 更新的情形。2026-10-13 一夜的随机压力测试（几万个配置：多层、各层 TTL 不同、随机淘汰、租约层、批量读、共用分片的写入）找出了许多违反它的情形，为此先后加了：回填落下前后摘掉别人留着的在途回源；回源的结果拿着回填锁发布、分片纪元变过就先回填再发布；复制先读所有目标层并采纳最新的；租约被本进程拒绝时删掉租约层里更旧的条目（按 key 记录本进程持有的租约）；回填被写入跳过时改为发布各层里现有的条目。每补一处，下一轮又冒出新的窗口，有两次修补还引入了回归（一次让多实例的共享层在每次同时未命中后被清空）；拿着回填锁发布还让有并发回填时的大批量 `GetMany` 明显变慢（误判按分片计数）。剩下的两族（复制看不到它读来源层之后的淘汰、腐烂、删除；写入之后两次问数据源重叠、数据源又被绕过修改）要改回源流程的结构才能修，而数据源不给版本号，靠 `CachedAt` 排序永远有淘汰窗口，修不完美。

而这条保证在实际部署里价值不大：多个实例跑在负载均衡后面，同一个用户的连续请求多半落在不同实例上，别的实例的内存层在广播到达之前本来就可能是旧的，用户照样会看到新值之后又是旧值。真正有价值的是写入相关的保证。所以收窄为：

- **保证**：`Set`/`Del` 返回之后，这个进程不再返回写入之前的值，各层也不留着它（写入顺序守卫，[ADR 0003](0003-striped-backfill-guard.md)）；写入摘除在途回源时先删 `sourcing` 的登记、再摘合并回源，计数写入之前先摘，避免写入之后两次问数据源重叠而旧答案后落下。
- **尽力而为**：只靠 TTL、数据源被绕过修改时，上面两件便宜的机制消除常见的乱序；遇到淘汰、腐烂、并发刷新卡在窗口里，读到的值可能短暂倒退，直到下一次回填或腐烂。
- 那一夜加的那些机制全部撤回，代码回到它们之前的样子（`read.go`、`lease.go` 回到提交 `c36c448`）；对应的测试和复现一起删掉，撤回的理由就是本节。
