# 同一个进程里，读到的值不倒退

写入顺序守卫（[ADR 0003](0003-striped-backfill-guard.md)）只挡住 `Cache` 自己的写入。数据源被绕过 `Cache` 修改、只靠 TTL 更新时，两次回填之间还会乱序，读者先读到新值、再读到旧值：

- **复制和刷新撞上**：第一层没有、第二层陈旧时，读取把第二层的 v1 复制上来；刚读完还没回填，刷新就把数据源的 v2 写进两层；复制随后落地，第一层回到 v1。
- **两次问数据源重叠**：刷新正在问数据源，普通读取又问了一次，先返回的那次读到了更新的值，后返回的旧值又写了回去。原来的 `WithFetchesPerKey(n)` 让同一个 key 的 n 次读取回源也能这样重叠（已删除，见 [ADR 0021](0021-one-fetch-per-key.md)）。

我们做了两件事：

1. **回填之间按分片排队，从下层复制的条目不覆盖更新的答案**：回填拿到分片读锁、核对完写入代数之后，再拿分片的回填锁；复制上来的条目先读一遍它要写的各层（打开了租约的层也读），取其中最新的条目往上写；目标层的条目 `CachedAt` 更晚就不写这一层。（2026-10-13 补：原来租约层不读，以为只有持有租约的回源能写它；但持有者可能是本进程较早的刷新，落下的答案比本进程已经返回的旧。）
2. **同一个 key 同时只问一次数据源**：问数据源之前在 `sourcing` 里登记；已经有别的回源在问，就等它的结果，不再问。登记在回填之后才注销，写入摘除它。

3. **回填落下前后，摘掉别人留着的在途回源**（2026-10-13 补）：一次回源发布之后、回填完成之前一直登记着，读第一层未命中的请求会加入它、拿到它已经发布的结果。刷新在这期间落下了更新的答案、第一层的这个条目又被淘汰时，之后的读加入那个旧的回源，就倒退了。所以回填在写各层之前、以及写完还拿着回填锁时，各摘一次这个 key 上别的读取回源（自己的留着，读者照样在回填期间加入它）。代价是未命中多两次加锁，`BenchmarkGet/miss` 约慢 6%。

4. **回源的结果拿着回填锁发布，第一层可能有更旧的条目时先落下再发布**（2026-10-13 补）：原来回源一有结果就发布、再回填。普通回源读第一层未命中之后，刷新把数据源较早的回答 v1 写进了各层；普通回源随后问到 v2、发布，读者拿到 v2，下一次读命中第一层的 v1，倒退。现在发布要先拿回填锁（别的回填不会在发布和写完第一层之间落下）；读第一层之后分片纪元变了（有回填或写入落下过），或者是刷新的回源（它替换的陈旧条目还在被返回），就写完各层再发布。复制上来的条目遇到目标层更新的条目，改用更新的那个继续往上写、作为结果发布，否则晚发布的旧副本仍会被在别人的回填期间加入它的读拿到。代价是等待方要等同一个分片上正在进行的回填，纪元变了时还要等自己的回填写完。分片纪元按分片计数，同一个分片上别的 key 落下回填也算「变了」，所以会误判：实测 `BenchmarkGetMany/half-miss/n=1000` 里上一轮的后台回填和这一轮交错，约 44% 的 key 走了先写完再发布，这个基准从约 283µs 变成约 488µs；单个 key 的 `BenchmarkGet/miss` 不变。要消除误判，得在拿着回填锁时再读一次第一层，第一层是远程层时这一读不便宜，所以没有做。

5. **没领到租约的回填，删掉那一层里更旧的条目**（2026-10-13 补）：一次读在租约层被拒（持有者是本进程的刷新），刷新先落下了较早的答案，这次读随后问到更新的答案，却不能写那一层，于是那一层留着旧值，等上面的层腐烂就读到它。它不能写（可能盖过别的实例的写入），但可以删：拿着回填锁读一下那一层，条目比自己的答案旧（数据源的答案，同一时刻的也算）就删掉，删除永远不会让旧值复活，代价是被拒时多读一次那一层、偶尔多一次未命中；删除是写入，会结束那个 key 的租约，持有者还没落下的话它的 `PutLeased` 就什么也不写。

五件合起来，数据源的回答按顺序落下，复制又不会盖过它们，同一个进程里读到的值不会倒退。

## 考虑过的方案

- **不回填下层的陈旧条目**：消除第一种，但第一层会在条目陈旧的整段时间里空着，每次读都去下层；数据源宕机、刷新一直失败时尤其明显。也不解决第二种。
- **复制上来的条目马上腐烂**：没用，问题是覆盖，不是寿命。
- **数据源的回答也做比较**：同一个 key 同时只问一次之后，没有更新的回答会在它之前落下，读这一次是白花的。
- **只做比较、不合并问数据源**：两次重叠的回答排不出先后：按回答时间，后返回的旧值会赢；按开始时间，先开始、后读到新值的会输。没有数据源的版本号，只能不让它们重叠。
- **一律先回填、再发布**：也消除第 4 种，但每次未命中的等待方都要等各层写完（共享层是一次网络往返）。只在分片纪元变了时这样做，常见的未命中不受影响。
- **比较时在后端里原子地「比较后写入」**：每个后端都要多一个原子操作（Redis 要 Lua、表要条件更新）。进程内排队之后，比较和写入之间不会再有别的回填插进来，用不着。

## 后果

- 未命中多一次登记（`sync.Map`，3 次分配）；纯内存的未命中基准约慢 15%，真实的未命中还要加上数据源的往返。
- 「上层未命中、下层命中」的复制多读一次上层（通常是内存层）。
- 回填之间会互相等（同一个分片），但从不等写入；批量回填按分片编号拿回填锁，不会死锁。
- 每个分片多 8 字节，一个 `Cache` 多 32 KB。
- 其他实例的写入经共享层到达这个实例的内存层时，没有这个顺序保证；那要靠失效广播（见 [ADR 0023](0023-invalidation-broadcast.md)）。
