# gormcachex 只认完全相等的 key，MySQL 只支持 utf8mb4_0900_bin

缓存 key 区分大小写和末尾空格，但 MySQL 默认的排序规则（`utf8mb4_0900_ai_ci`）既不区分大小写、也不区分重音。在这样的表上，`Set("ABC")` 之后 `Get("abc")` 会读到 `ABC` 的值，`Set("abc", x)` 会把 x 写进 `ABC` 的那一行。我们做了三件事：

1. 只支持 `key` 列为 `utf8mb4_0900_bin` 的 MySQL 表，大小写和末尾空格都精确比较。`Migrate` 建表时使用它，这要求 MySQL 8.0.17 及以上（MariaDB 没有这个排序规则），所以建表前会先检查版本；表已经存在时，检查 `key` 列的排序规则，不符合就返回错误，并给出转换语句。
2. `Get`/`GetMany` 只返回存储的 key 和请求的 key 完全相等的行；
3. upsert 时连同 key 列一起改写，所以共用的一行只属于最后写入它的 key。

第一点从根上避免冲突；后两点是多一道防线：万一碰上不符合的表（比如没调 `Migrate`、自己建的表），只差大小写的 key 会互相挤占同一行，表现为多几次未命中，但**不会读到别的 key 的值**。

## 考虑过的方案

- **大小写不敏感地匹配**：只是让 `GetMany` 和 `Get` 错得一样，读到别的 key 的值这个问题依然存在。
- **`utf8mb4_bin`**：支持更老的 MySQL，但它是 PAD SPACE 排序规则，会忽略末尾空格，`"a"` 和 `"a "` 仍会共用一行。我们选择只支持 MySQL 8.0.17 及以上。
- **改写已有表的排序规则**：会对用户的表执行 ALTER，锁表时间和风险不应由库来承担。`Migrate` 只报错并给出语句，由用户自己执行。
- **继续支持已有的 `*_ci` 表**：只差大小写的 key 会共用同一行，批量写的加锁顺序也不再是字节序，只能靠重试兜底。v1 的 GORM 后端读取时用了未加引号的 `key`，在 MySQL 上本来就报语法错误，实际没有需要兼容的老表。

## 后果

- 不支持 MySQL 8.0.17 以下的版本和 MariaDB。
- 用 MySQL 默认配置建的表要先手动转换，`Migrate` 才会通过；不调 `Migrate`、自己建表时，必须用 `utf8mb4_0900_bin`。
