# gormcachex 不进调用方的事务

v2 起初保留了 v1 的做法：`gormcachex.WithTx(ctx, tx)` 让带这个 ctx 的写入在调用方的事务里执行。这会造成数据库检测不到的死锁：事务 1 写了 key k，行锁要到提交才放；事务 2 写 k，先拿到 k 的分片锁，再在数据库里等事务 1 的行锁；事务 1 在同一个事务里再写 k（或者同一分片的另一个 key），在分片锁上等事务 2。数据库只看得到其中一把锁，两边会一直等下去，直到 ctx 结束。同一个根源还带来两个问题：一批写入分成「写」和「删」两条语句时，两遍各自排序的加锁合起来不是一个全局顺序，两个事务可能互相死锁且不重试；写入失败后的失效在事务外执行，会去等事务自己持有的行锁。

我们删掉了 `WithTx` 和 `TxFrom`。gormcachex 的每条语句都独立提交，行锁只在一条语句里持有，跨语句、跨调用都不持有；死锁的受害者总能重试（见 [ADR 0010](0010-gorm-deadlock-ordering-and-retry.md)）。

## 考虑过的方案

- **保留 `WithTx`，带事务的写入不持分片锁等数据库**：核心要认识「调用方的状态」，还要另外证明写入顺序在各层仍然一致；改动大、难验证。
- **保留 `WithTx`，只在文档里提醒**：死锁一旦发生就是整个请求卡住，不是偶发的报错，不能靠使用者小心。

## 后果

- 想让缓存表和数据源在同一个事务里一起提交，已经做不到了。这本来也只是一半：上面的内存层、Redis 层不会跟着事务回滚。正确的用法一直是：在事务里改数据源，提交之后再 `Set`/`Del`。
- 确实需要在事务里写这张表时，可以用 `gormcachex.New(Config{DB: tx, …})` 临时建一个后端直接写，不经过 `Cache`。
- `cachex.IsShared` 仍然保留：它是核心给所有后端的约定，自己写的后端如果从 ctx 里取调用方的状态，要看这个标记（[ADR 0007](0007-detached-fetch-context.md)）。gormcachex 已经不需要它。
