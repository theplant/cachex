# v2：一个 Cache 管所有层，寿命由 Cache 计算并记在条目里

v1 里每一层是一个 `Client`，靠「上一层的上游是下一层 Client」串起来。这带来了三个问题：单 key 和批量各有一份读路径；上层要对 `*Client` 做类型断言，递归计算下层的超时预算；条目的时间戳只能靠用户把值包进 `Entry[T]`，一层层往上传。

v2 只有一个 `Cache[T]`，用 `cachex.New(source, layers, opts...)` 构造。`layers` 是从上到下排好的若干层，每层是一个后端加上这一层的 TTL 配置：

- **一个 key 只有一个在途回源、一套分片锁**。最上层未命中才认领回源；领头请求依次读下面各层，都没有可用条目时才问数据源；拿到结果后，在同一把分片读锁下回填它上面所有没命中的层。
- **后端存的是条目 `Entry[T]`**：值或「不存在」、数据源回答的时间 `CachedAt`、这一层的 `FreshUntil` 和 `ExpiresAt`。用户的类型只出现在 `T` 里，选项都和 `T` 无关。不存在记录是条目的一种状态，不再需要第二个后端，未命中也少一次后端读取。
- **寿命由 Cache 计算**：每层 `TTL(fresh, stale)` 和 `NotFoundTTL(fresh, stale)` 从 `CachedAt` 起算；新鲜期按 `Jitter` 随机缩短（只缩短、不延长，「最多返回多旧的数据」不受影响）；`WithMaxAge(func(T) time.Duration)` 给单个值设寿命上限，在回源拿到值（或 `Set` 写入值）时调用一次。条目从下层复制到上层时，`CachedAt` 不变，上层的 `FreshUntil`、`ExpiresAt` 都不晚于下层，所以年龄不会在每层重新计时。
- **后端不再有自己的 TTL 配置**：后端用条目的 `ExpiresAt` 当原生过期时间。v1 里「后端 TTL 要不小于新鲜期加陈旧期」的坑没有了。
- **写入从最下层写到最上层**，这是 ADR 0002 的「先写上游再写本层」挪进了 Cache 内部；某一层写失败，就删掉它和它上面各层的条目。`SetMany`/`DelMany` 按分片编号从小到大加锁，避免两个批量写互相等待。
- **`Del` 只失效，不记录不存在**：删掉各层的条目，下次读取再问数据源。v1 的 `Del` 在配置了不存在缓存时会记下「不存在」，而「先改数据源再 `Del`」常常是更新而不是删除，于是更新过的 key 会在不存在记录的新鲜期内读不到。

## 考虑过的方案

- **保留一层一个 Client，只合并两份读路径**：条目的时间戳仍要靠类型断言跨层传递，超时预算的递归也去不掉。
- **值自带过期时间，通过一个接口（`ExpiresAt() time.Time`）实现**：选项能保持和 `T` 无关，但第三方类型加不了方法，只能包一层。所以改成函数选项 `WithMaxAge`，`T` 由函数参数推导，类型对不上时 `New` 直接 panic。
- **保留自定义的新鲜度函数 `WithStale(func(T) State)`**：它能做的事里，「值自带过期」和「按状态区分寿命」由 `WithMaxAge` 覆盖；「按版本号整体作废」更适合把版本号放进 key。

## 后果

- 不兼容 v1：API、后端存储格式都变了。缓存数据可以丢弃，升级只是一次冷启动。
- 只有一套读路径，也只有一套写路径；`Get` 保留一个命中时不分配内存的快路径，单 key 的未命中和写入也各有一条不建 map 的快路径。
- `GetMany` 把未命中的 key 一次全部认领，下面每层才能一次读完。代价是数据源不支持批量时，一个 `Get` 碰上 `GetMany` 里还在排队的 key，要等它轮到；v1 在这种情况下是轮到哪个 key 才认领哪个。
- 每一层的 TTL 配置在 Cache 里，换后端不用改 TTL；后端变成纯粹的存储。
