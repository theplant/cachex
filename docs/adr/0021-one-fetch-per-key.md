# 一个 key 同时只有一次读取的回源

v1 的 `WithFetchConcurrency`、v2 原来的 `WithFetchesPerKey(n)` 允许同一个 key 同时有 n 次回源：请求随机落进 n 份登记中的一份。理由是「用下层多一些负载换吞吐」「避免单个慢回源拖住所有请求」。我们删掉了这个选项，同一个 key 的并发未命中总是共用一次回源（后台刷新仍另有自己的一次，见 [ADR 0016](0016-refresh-has-its-own-flights.md)）。

## 为什么删

- **吞吐不会更高**：一次回源的结果同时发给所有等待方。分成 n 份，每份的等待方等的仍是差不多同时开始的那次回源，谁也不会更早拿到结果，只是数据源被问了 n 次。
- **挡慢回源只挡一小部分**：请求随机落进一份，不是「慢了换一份」。落进慢的那份照样被拖住；数据源整体变慢时，n 份一起慢，还多给它 n-1 倍的压力。单次回源卡住时，调用方的 ctx 一到期就返回，回源本身也被 `WithFetchTimeout` 限住。
- **它让同一个 key 的回源在时间上重叠**：两次重叠的读在数据源被绕过 `Cache` 修改时，分不出谁读到的更新，回填可能让读者先看到新值、再看到旧值。没有数据源的版本号，这在原理上排不出先后；只有不让它们重叠才能根除。
- 实现上的代价：登记的 key 里多一个 `slot`，写入要摘除 n+1 份登记，二次检查要靠读 key 本身让各份收敛。

## 考虑过的方案

- **保留，在文档里写明代价**：默认值是 1，几乎没人会改；留着它就留着一个只在改了它时才出现的一致性漏洞。
- **改成对冲（回源超过某个时间还没回来，就再发一次，所有等待方取先到的）**：这才是挡慢回源的正确做法，但同样会让回源重叠。真需要时再做，并且要让对冲的结果走同一套回填排序。

## 后果

- `WithFetchesPerKey`、`DefaultFetchesPerKey` 删除；v1 的 `WithFetchConcurrency` 在 v2 里没有对应（MIGRATION 已写）。
- 在途回源的登记 key 只剩 `{key, refresh}`，写入摘除固定两份。
