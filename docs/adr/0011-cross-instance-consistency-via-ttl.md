# 跨实例一致性暂时靠 TTL 兜底

分片锁和在途回源的登记都只在一个 Client 的内存里，因此只能在一个进程内保证写入顺序。多个实例共用 Redis 或数据库时，有两件事不保证：其他实例的内存层看不到你的写入；一个实例可能在另一个实例写入之后，把旧值回填进共享层。这个 PR **不处理**它们，交给 TTL 兜底，并在文档里写清边界和 TTL 的设置建议。

## 考虑过的方案

- **带版本的条件写**：值要带上数据源的版本号，删除还要留墓碑。对数据源的要求太高，通用库做不到。
- **延迟双删**：写完后过一段时间再删一次。只能缩小窗口；回填比延迟还慢，或者进程在第二次删除前退出，就失效了；库里还要为每次写入挂一个定时任务。不建议做进库里。
- **Redis 租约（lease）**：能彻底解决旧值回填，还能顺带做跨实例的回源去重，而且不要求数据源提供版本号。但它需要新的可选接口、Lua 脚本、批量领租约，是一个独立的功能，放进待办。
- **失效广播（Redis Pub/Sub）**：解决其他实例的内存层看不到写入的问题，但断线时会丢消息，仍要靠 TTL 兜底。作为可选功能放进待办。

## 后果

- 多实例部署时，内存层和共享层的 TTL 都要按「能接受旧数据存活多久」来设，见 [consistency.md](../design/consistency.md)。
- 两项后续工作都记在 [todo.md](../todo.md) 里。
