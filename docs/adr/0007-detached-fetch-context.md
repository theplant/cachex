# 回源用共享 ctx：脱离领头请求的取消，后端不用调用方的状态

一次回源服务的是这个 key 的**所有**等待方，但认领它的只是其中一个请求。所以认领成功后，整个回源（二次检查、读下面各层、问数据源、回填）用的 ctx 是：保留领头请求 ctx 里的值（trace 等），去掉它的取消和截止时间，并打上共享标记，`cachex.IsShared(ctx)` 为真。每次调用各自受 `WithFetchTimeout` 限制。写入失败后的失效、后台刷新也用这样的 ctx。

后端看到共享标记，就不使用调用方放进 ctx 的状态。目前唯一的例子是 `gormcachex`：带共享标记时不用 `WithTx` 放进来的事务。

## 要避免的问题

- 二次检查如果用领头请求的原始 ctx，领头请求一放弃，二次检查就因为 ctx 已取消而失败，然后照样往下回源：缓存里明明已经有值，还是多打了一次。
- 回填如果用到领头请求的业务事务：这个事务一旦已经结束，回填就会失败；如果事务还在进行，回填会跟着它一起提交或回滚。

## 考虑过的方案

- **核心直接去掉 GORM 事务**：v1 就是这样做的，核心因此认识了一个后端的 ctx key。v2 改成通用的标记，由后端自己决定（[ADR 0013](0013-batch-backends-in-subpackages.md)）。
- **连 ctx 里的值也全部去掉**：trace 就断开了，而且没有通用的办法只保留一部分值。

## 后果

- 领头请求的 ctx 结束时，它自己立即返回，回源继续为其他等待方服务。
- 二次检查有独立的超时，不会无限期挂在一个卡住的后端上。
- 写入（`Set` 等）用的是调用方自己的 ctx，所以 `gormcachex.WithTx` 对写入生效；失败后的失效不在事务里。
- 自写后端如果也从 ctx 里取调用方的状态，要检查 `IsShared`。
