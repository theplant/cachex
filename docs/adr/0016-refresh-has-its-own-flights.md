# 刷新有自己的在途回源

> 「普通回源和刷新可以同时问数据源」这一点，已由 [ADR 0022](0022-reads-never-go-back.md) 改为在问数据源那一步合并。

刷新的目的是换掉陈旧的条目，所以刷新时下层的陈旧条目不算数：要么找到新鲜的条目，要么问数据源。原来刷新和普通读取共用一套登记（`flightKey{key, slot}`），于是刷新可能加入一次普通回源；普通回源会接受下层的陈旧条目，刷新就这样结束了，根本没问数据源，第一层只是换上一份同样陈旧的条目。反过来，普通读取加入刷新，就得等数据源，而下层明明有一个可以先返回的陈旧条目。

我们给 `flightKey` 加了 `refresh` 一项：刷新认领自己的在途回源，从不加入普通回源，普通读取也不加入刷新。写入摘除一个 key 的在途回源时，两种都摘。

## 考虑过的方案

- **普通回源也不接受下层的陈旧条目**：只要一套登记，但第一层未命中、第二层陈旧时，读取就要同步等数据源，失去了下层返回陈旧值的好处。
- **刷新加入普通回源后，看结果是不是来自数据源，不是就再回源一次**：刷新可能要等两次，还要把结果的来源一路带回来。

## 后果

- 同一个 key 的普通回源和刷新可以同时进行。刷新进行中第一层的条目腐烂了，普通读取不会加入刷新，而是自己回源，最多多问一次数据源。
- 写入每个 key 要摘除两份登记（`WithFetchesPerKey(n)` 时是 n+1 份：刷新的 `slot` 恒为 0），分散的写入基准约慢 5%。
- 每个 key 同时只有一次刷新，靠的是 `refreshing`（`sync.Map`）：查已有的 key 不加锁，返回陈旧值的命中不用去拿登记表的锁。曾经试过删掉它、只靠认领刷新的在途回源去重，结果 `Get/stale-hit` 慢了约 10ns（71ns → 81ns），又没有可测的好处，所以留着。刷新的在途回源固定在 `slot` 0，写入少摘几份登记。
