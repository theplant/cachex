# 默认的二次检查改为按需：只在读取之后本层被写过时才再读

`DoubleCheckAuto`（默认）以前的规则是「配置了不存在缓存就开启」。这个规则和二次检查什么时候有收益关系不大：收益取决于后端读的响应时间和 key 的热度。现在的规则是：请求在读后端之前记下 key 所在分片的分片纪元（写入次数加回填次数）；认领回源时，只有分片纪元变了（说明读取之后本 Client 往这个分片写过东西），才再读一次。没人写过，再读一次也只会读到同样的未命中。

## 实测

见 [research/2026-10-double-check.md](../research/2026-10-double-check.md)。后端读延迟 1ms、上游 5ms、一个热点 key 每毫秒 20 次请求：

| | Enabled | 新的 Auto | Disabled |
|---|---|---|---|
| 热点 key：上游调用次数 | 18 | 19 | 30 |
| 8000 个冷 key：每次 Get 读后端的次数 | 2.000 | 1.005 | 1.000 |

## 考虑过的方案

- **总是开启**：热点 key 的收益最大，但冷 key 和不存在的 key 每次未命中都要多一次后端往返，对远程 Redis 约多 0.5ms 延迟，而且永远没有收益。
- **按后端类型判断**（内存后端关闭，其他开启）：要维护一份后端类型清单，用户自定义的后端也判断不了。
- **删掉二次检查**：远程后端上的热点 key，上游调用会多出约 60%（30 次对比 18 次）。

## 后果

- 和其他 key 共用一个分片、并且被写过时，会多读一次（实测 0.5%），但永远不会漏掉一次该做的检查。
- 看不到**其他进程**写进共享层的值；需要这一点时用 `DoubleCheckEnabled`。
- 这是相对 main 的默认行为变化：配置了不存在缓存的用户，冷 key 上不再二次检查；没配置的用户，热点 key 开始二次检查。
