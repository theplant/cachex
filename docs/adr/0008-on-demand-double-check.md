# 默认的二次检查按需进行：只在读取之后被写过时才再读

`DoubleCheckAuto`（默认）的规则是：请求在读第一层之前记下 key 所在分片的分片纪元（写入次数加回填次数）；认领回源时，只有分片纪元变了（说明读取之后本 `Cache` 往这个分片写过东西），才再读一次第一层。没人写过，再读一次也只会读到同样的未命中。v1 的规则是「配置了不存在缓存就开启」，这和二次检查什么时候有收益关系不大：收益取决于第一层读的响应时间和 key 的热度。

## 实测

见 [research/2026-10-double-check.md](../research/2026-10-double-check.md)。第一层读延迟 1ms、数据源 5ms、一个热点 key 每毫秒 20 次请求：

| | Enabled | Auto | Disabled |
|---|---|---|---|
| 热点 key：数据源调用次数 | 18 | 19 | 30 |
| 8000 个冷 key：每次 Get 读第一层的次数 | 2.000 | 1.005 | 1.000 |

## 考虑过的方案

- **总是开启**：热点 key 的收益最大，但冷 key 和不存在的 key 每次未命中都要多一次往返，对远程 Redis 约多 0.5ms 延迟，而且永远没有收益。
- **按后端类型判断**（内存后端关闭，其他开启）：要维护一份后端类型清单，用户自定义的后端也判断不了。
- **删掉二次检查**：远程的第一层上的热点 key，数据源调用会多出约 60%（30 次对比 18 次）。
- **读完第一层之后再记分片纪元**：命中时能省一次哈希，但第一层读得慢时，读取期间发生的回填会被算进去，正好漏掉该做的检查。

## 后果

- 和其他 key 共用一个分片、并且被写过时，会多读一次（实测 0.5%），但永远不会漏掉一次该做的检查。
- 看不到**其他进程**写进共享层的值；需要这一点时用 `DoubleCheckEnabled`。
