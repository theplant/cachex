# GetMany 按段认领

`GetMany` 原来一开始就认领全部未命中的 key，下面每层一次读完，只有问批量数据源时才按 `WithGetManyChunkSize` 分段。认领一次全部，带来两个问题：

- 数据源不支持批量时，key 只能按每次 `WithGetManyConcurrency` 个的队列逐个查。一个并发的 `Get` 碰上队尾的 key，要等这次 `GetMany` 排到它：1000 个 key、并发 16、每次查询 10ms 时，等约 630ms，而它自己查只要 10ms。
- 分段只做了一半：下层命中的 key 不分段，一次大 `GetMany` 回填它们时，仍然一次占住大量分片。

我们把 `WithGetManyChunkSize` 的含义扩大成「一段多少个 key」：一段开始时才认领它的 key，这一段每层一次调用读完、问数据源（批量数据源一次调用，普通数据源每个 key 一次 `Get`）、各自回填。一段只在数据源请求的并发名额够用时才开始：批量数据源每段占一个名额，普通数据源占 `min(分段大小, 并发数)` 个。还没开始的段不认领，所以别的请求读到其中的 key 会自己回源；调用方的 ctx 结束后，不再开始新的段。分段大小默认 0，全部一段，和原来的行为一样。后台刷新多个 key 时也按段进行。

## 考虑过的方案

- **只在「数据源不支持批量、且只有一层」时退回逐个认领**：只解决一种组合，读路径多一个特例；有下层的情况仍然一样。
- **逐个认领**：有下层时，下层只能逐个读，`GetMany` 一段 key 只往返一次的意义就没了。它其实就是分段大小为 1 的特例。
- **另加一个选项控制认领粒度**：和 `WithGetManyChunkSize` 分不清，用户要同时理解两个「段」。
- **默认给一个分段大小**：用多层的用户什么都不改，读下层的往返次数就会变多，例如 Redis 热、内存层空时，原来一次拿全，现在要好几次。行为变化应当由用户选择。

## 后果

- 认领仍然当场给出答案，处理一段的 goroutine 只回源自己领头的 key，别人领头的由调用方最后统一等，所以重叠的 `GetMany` 仍然不会死锁（[ADR 0001](0001-own-flight-group.md)）。
- 设了分段大小，读下层的调用次数变成每层 ⌈未命中数 / 分段大小⌉ 次；批量数据源时段与段并发，普通数据源时一段占满并发名额，下一段等它。
- 一段只有一个 key 时，即使数据源实现了 `BatchSource`，也用 `Get` 问，和单个 key 的回源一致。
- 后面的段更常做二次检查：前面的段的回填会改变分片纪元。多一次读第一层，也正好能接住别的请求刚查到的结果。
- 调用方放弃之后，还没开始的段不再回源，不会白白打数据源。
