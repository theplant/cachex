# 用分片锁和写入代数防止旧值回填

一次回源读到旧值后，可能在一次 `Set`/`Del` 完成之后才回填，悄悄撤销这次写入。我们把 key 按哈希分进固定 4096 个分片，每个分片有一把读写锁和一个写入代数：`Set`/`Del` 持写锁，写完上游后把写入代数加 1；回填用 `TryRLock` 拿读锁，并且只在写入代数和回源前记下的一样时才写。所以回填要么在写入之前落下（随后被覆盖），要么被跳过，永远不会在 `Set`/`Del` 返回之后落下；读也永远不会等写。

## 考虑过的方案

- **每个 key 一把锁**：锁的数量随 key 数无限增长；要安全删除，就得加引用计数和一把全局锁。
- **回填后发现期间有写入，再删掉本层条目（撤销式）**：这是本 PR 的第一个版本。缺点是在「回填落下」和「被删掉」之间，读者能看到旧值。
- **带版本的条件写**：值要带上数据源的版本号，写入时只在版本更新时才覆盖。对数据源的要求太高，通用库做不到。
- **只做摘除在途回源**：能挡住「加入更早的回源」，但挡不住已经开始的回源在写入后回填。cachex 两者都做，见 [write-order.md](../design/write-order.md#摘除在途回源)。
- **分片数 1024 还是 4096**：4096 让跨 key 的写入排队、被跳过的回填、多余的二次检查都减少到四分之一，代价是每个 Client 的内存从 32KB 增加到 160KB。这个数字很容易调整，不单独成篇。

## 后果

- 落在同一个分片的不同 key 会互相影响：写入排队，或者回填被跳过（多一次未命中），但永远不会读到错的值。
- 一次大批量回填会在回填期间占住它所有 key 的分片（1000 个 key 约 22%）；用 `WithGetManyChunkSize` 可以让每段各自回填、只占自己的分片。
- 等写锁时要能被 ctx 取消，所以加锁用了「`TryLock`，拿不到就开 goroutine 去 `Lock` 并同时等 ctx」的写法；放弃等待的写入，会在分片空出来后删掉本层条目。
- 只在单个进程内成立，见 [ADR 0011](0011-cross-instance-consistency-via-ttl.md)。
