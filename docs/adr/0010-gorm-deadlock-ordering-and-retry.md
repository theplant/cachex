# GORM 并发写的死锁：统一加锁顺序加有限重试，不锁表

多个实例同时回填有重叠的 key 时，`SetMany` 按 Go map 的随机顺序插入行，两条语句会以相反的顺序锁行，造成死锁。PostgreSQL 上还有第二个来源：`DELETE` 按索引顺序加锁，而索引顺序跟着列的排序规则走（官方镜像默认是 `en_US.utf8`），和字节序不一致。我们的做法是：`SetMany` 插入前按 key 的字节序排序；PostgreSQL 的 `DelMany` 先用 `ORDER BY key COLLATE "C" FOR UPDATE` 按字节序锁好行，再删除；剩下的少量死锁（MySQL 的间隙锁，InnoDB 要求应用重试）会重试，最多执行 5 次（即重试 4 次），在调用方自己的事务里则不重试。

## 实测

并发混合执行 `SetMany` 和 `DelMany`（[research/2026-10-gorm-deadlock.md](../research/2026-10-gorm-deadlock.md)）。第一行来自第一轮（8 个 worker，共 320 次操作），其余来自第二轮（16 个 worker，共 1280 次操作）：

| 方案 | MySQL 8.4 | PostgreSQL 16 |
|---|---|---|
| 只给 `SetMany` 排序（修复前，第一轮） | 2 / 320 次死锁 | 149 / 320 次死锁，每次卡 1 秒 |
| 统一加锁顺序 | 3 次死锁，949 ops/s | 0，1922 ops/s |
| **统一顺序 + 重试（采用）** | **0，840 ops/s** | **0，1936 ops/s** |
| 锁表（整表串行写） | 0，647 ops/s（-32%） | 0，1045 ops/s（-46%） |

## 考虑过的方案

- **锁表**：死锁也能降到 0，但吞吐损失随并发上升（8 个 worker 时约 -20%，16 个时 -32% 到 -46%）。上表的锁表实现在 MySQL 上提交前就释放了锁，不够严格；改成严格锁表后复跑两遍，损失是 -41% 到 -50%，见研究报告的「复跑脚本的完整验证」一节。缓存层正是高并发的地方，代价太大。
- **只重试、不统一顺序**：PostgreSQL 上反而更糟，重来一遍还会撞上；第一轮的 320 次操作跑了 460 秒。
- **改用 READ COMMITTED 隔离级别以减少间隙锁**：MySQL 上的死锁反而更多。

## 后果

- 死锁的识别要区分驱动：PostgreSQL 用 SQLSTATE；MySQL 只能匹配错误文本 `Error 1213 (40001)`，因为 go-sql-driver 的错误类型没有 SQLState 方法。驱动如果改了错误格式，MySQL 这边的重试就会失效。
- 老的 MySQL `*_ci` 表的索引顺序不是字节序，那里只能靠重试兜底。
