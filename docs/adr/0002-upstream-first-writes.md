# 写入先写下层、再写上层，任何失败都删掉失败层及其上面的条目

`Set`/`Del`/`SetMany`/`DelMany` 从最下层写到最上层；第 j 层写失败时，删掉第 j 层和它上面所有层的这个 key，然后返回错误。理由是：上层不能出现下层没有的值。如果先写上层、下层却写失败了，上层就会一直挂着一个「从未真正发生过」的值，直到 TTL 到期。一层写失败时，它的状态是未知的（可能已经写进去了，只是回复丢了），所以不能猜，只能删掉，让下次读取取真实状态。写入从不写数据源。

## 考虑过的方案

- **先写上层**：写入一返回，最快的那层马上可见；但下层失败时会留下上层有、下层没有的值。
- **只删、不写（cache-aside 的经典做法）**：删除总是安全的；但 `Set` 之后的第一次读必须回源。在「先改数据库、再 `Set`」的用法里，`Set` 就退化成了 `Del`，失去了意义。分片锁已经保证了写入顺序（[ADR 0003](0003-striped-backfill-guard.md)），写入各层是安全的，所以保留写入。

## 后果

- 写入过程中有一个短暂窗口：上层落下之前，并发读仍会读到旧值。写入返回后窗口关闭。
- 下层写成功、上层写失败时，返回错误，但下层的改动**不回滚**。返回错误不代表什么都没写进去。
- 一层删除失败时，紧接着的失效同样删不掉，这一层可能留着旧条目，直到它过期；失效失败记 WARN 日志。
- v1 里这条规则体现为「先写上游 Client，再写本层」；v2 一个 `Cache` 管所有层，规则挪进了 `Cache` 内部，见 [ADR 0012](0012-one-cache-over-layers.md)。
