## 1. 过期时间抖动（防缓存雪崩）

- **问题：** cachex 用合并回源防击穿、用不存在缓存防穿透，但没有防**雪崩**的机制：同一时刻写入的大量 key（冷启动预热、一次 `GetMany` 回源取回 1000 个 key）会在同一时刻一起过期，届时大量请求同时回源。`EntryWithTTL` 的新鲜度判断完全确定，只看 `CachedAt + freshTTL`；Redis 等后端的 TTL 也是固定值。
- **做法：** 加一个可选的抖动比例（例如 `WithTTLJitter(0.1)` 表示正负 10%），按 key 的哈希计算一个固定的偏移量：不用额外存储，同一个 key 每次判断结果一致。后端 TTL 的抖动在各后端的配置里单独考虑。
- **注意：** 默认关闭，因为开启后会改变现有用户的过期时间。

## 2. 多实例一致性

分片锁只在单个 Client 所在的进程内保证顺序。多个实例共用 Redis 等下层时，下面两点目前只靠 TTL 兜底，见 [design/consistency.md](design/consistency.md) 和 [ADR 0011](adr/0011-cross-instance-consistency-via-ttl.md)。

### 2.1 Redis 租约：防止旧值回填进共享层，并做跨实例的回源去重

- **问题一（旧值回填）：** 实例 A 未命中，从数据源读到旧值；实例 B 随即写入数据源，并更新或删除共享缓存；A 再把旧值回填进共享缓存，旧值一直留到 TTL 到期。
- **问题二（跨实例回源）：** 部署 20 个实例时，每个实例的合并回源只在自己进程内生效。一个热点 key 过期，数据源会被回源 20 次。
- **做法：**
  - 读未命中时，用一段 Lua 原子地执行 `GET k`，若为空就写入 `lease:k = 随机令牌`，并返回令牌。读和领租约必须在同一个原子操作里。
  - 任何写入（Set/Del）都顺带删除 `lease:k`，让所有在途令牌作废（可以放进写入的同一个 pipeline）。
  - 回填用另一段 Lua：只有 `lease:k` 仍等于自己的令牌时才写入值。
  - 别的实例发现已有租约时，等待一小段时间再读，或者先返回陈旧值，不再回源。这就解决了问题二。
- **代价：** 往返次数不变；未命中时多写一个租约 key，回填改用 `EVALSHA`，写入多一个 `DEL`。不要求数据源提供版本号。
- **实现考虑：**
  - 新增可选接口（例如 `LeaseCache`），后端实现了它，Client 才走这条路；批量读要支持批量领租约。
  - 先做 `RedisCache`；`GORMCache` 视需要跟进（租约列或租约表，加条件更新）。
  - 延迟双删只能缩小窗口，进程退出就失效，不做进库里。

### 2.2 用 Redis Pub/Sub 广播失效（可选）

- **问题：** 一个实例上的写入到达不了其他实例的内存层，它们会一直返回旧值，直到过期。
- **做法：** 写入后在一个频道上发布被改动的 key，订阅的实例删除自己内存层里的这些 key。
- **注意：** 断线期间的消息会丢失，最终仍要靠 TTL 兜底。做成可选功能，默认关闭。

## 3. 小问题

- **单 key 的后台刷新把「不存在」也记成 ERROR：** `asyncRefresh` 在上游返回不存在时会记一条 `async refresh failed` 的 ERROR 日志，而批量的 `asyncRefreshMany` 会跳过不存在。main 上就是这样。应该统一成跳过不存在。
- **GORMCache 在 SQLite 上存不了 JSON 标量数字：** `T = float64` 这类值，SQLite 会把 JSON 存成数字类型，`datatypes.JSON` 读回来时扫描失败。结构体、字符串不受影响。需要确认 MySQL 和 PostgreSQL 上是否也有这个问题，再决定是在读取时兼容，还是在文档里说明限制。

## 4. GORM 缓存改进

### 清理 Worker

为 `GORMCache` 实现后台清理 worker，用于删除过期条目：

- **需求：**

  - 必须使用细粒度的分段操作（避免大批量删除）
  - 应持续运行，具有可配置的间隔时间
  - 删除策略：细水长流（例如每批 100 条记录）
  - 应考虑数据库负载并实现背压机制
  - 考虑添加监控指标以观察清理操作

- **实现考虑：**
  - 使用 `updated_at` 时间戳识别过期条目
  - 可配置的过期阈值（例如删除 7 天前的条目）
  - 支持优雅关闭（缓存关闭时停止 worker）
  - 可选：基于数据库性能的自适应分段大小

## 5. 热度统计

### 核心热度追踪功能

实现热度统计机制以跟踪缓存 key的访问模式：

- **需求：**

  - 跟踪每个 key的访问频率
  - 跟踪最后访问时间戳
  - 衰减机制以降低旧访问的权重
  - 高效的数据结构（例如并发 map 或时间窗口计数器）
  - 可配置的统计数据保留期限

- **需要追踪的指标：**
  - 每个 key的命中次数
  - 最后访问时间
  - 访问速率（每时间窗口的命中次数）
  - 可选：区分缓存命中和缓存未命中

### 用于热点 Key 记录的 CacheWrapper

实现一个 `CacheWrapper`，包装现有的 `Cache` 实现以记录热点 key：

- **需求：**

  - 包装任何 `Cache[T]` 实现
  - 基于访问模式记录最热的 N 个 key
  - 在 `Close()` 时导出热点 key列表以供持久化
  - 支持启动时读入热点 key进行缓存预热

- **使用场景：**

  - 识别应用重启时应预热哪些 key
  - 分析缓存访问模式
  - 优化缓存分配策略

- **API 设计考虑：**

```go
type HotKeyRecorder[T any] struct {
    backend Cache[T]
    stats   *HotnessStats
    topN    int
}

// 关闭时导出热点 key
func (h *HotKeyRecorder[T]) Close() (hotKeys []string, err error)

// 读入热点 key进行预热
// 注意：批量预热时（如使用 RistrettoCache），可以在所有 Set 操作完成后
// 最后统一调用一次 Wait() 来提升性能
func (h *HotKeyRecorder[T]) WarmUp(ctx context.Context, keys []string) error
```

### 基于热度的流量整形

实现流量整形机制以保护上游服务和数据库：

- **需求：**

  - 根据 key 的热度区分回源并发度
  - 热点 key：更高并发度（为大多数用户提供更快响应）
  - 冷门 key：较低并发度（保护数据库稳定性）
  - 渐进式限流以避免突发流量峰值

- **实现策略：**

  - 为热点/冷门 key维护独立的 回源并发限制
  - 热点 key阈值：可配置的百分位数（例如按访问率排名前 20%）
  - 冷门 key：使用较小的并发度或速率限制
  - 基于实时访问模式的动态调整

- **配置示例：**

```go
type TrafficShapingConfig struct {
    HotKeyConcurrency  int     // 例如 10
    ColdKeyConcurrency int     // 例如 2
    HotKeyPercentile   float64 // 例如 0.8（前 20%）
}
```

- **优势：**
  - 保护数据库免受冷门 key风暴的影响
  - 确保大多数用户（热点 key）的良好性能
  - 防止冷门 key的慢查询影响热点 key性能
  - 高负载下更好的资源分配
