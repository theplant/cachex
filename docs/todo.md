## 1. 多实例一致性

分片锁只在一个 Cache 所在的进程内保证顺序。多个实例共用 Redis 等层时，下面两点目前只靠 TTL 兜底，见 [design/consistency.md](design/consistency.md) 和 [ADR 0011](adr/0011-cross-instance-consistency-via-ttl.md)。

### 1.1 Redis 租约：防止旧值回填进共享层，并做跨实例的回源去重

- **问题一（旧值回填）：** 实例 A 未命中，从数据源读到旧值；实例 B 随即写入数据源，并更新或删除共享层；A 再把旧值回填进共享层，旧值一直留到条目过期。
- **问题二（跨实例回源）：** 部署 20 个实例时，每个实例的合并回源只在自己进程内生效。一个热点 key 过期，数据源会被回源 20 次。
- **做法：**
  - 读未命中时，用一段 Lua 原子地执行 `GET k`，若为空就写入 `lease:k = 随机令牌`，并返回令牌。读和领租约必须在同一个原子操作里。
  - 任何写入（`Set`/`Del`）都顺带删除 `lease:k`，让所有在途令牌作废（可以放进写入的同一个 pipeline）。
  - 回填用另一段 Lua：只有 `lease:k` 仍等于自己的令牌时才写入。
  - 别的实例发现已有租约时，等待一小段时间再读，或者先返回陈旧值，不再回源。这就解决了问题二。
- **代价：** 往返次数不变；未命中时多写一个租约 key，回填改用 `EVALSHA`，写入多一个 `DEL`。不要求数据源提供版本号。
- **实现考虑：**
  - 后端可选实现一个租约接口，Cache 检测到才走这条路；批量读要支持批量领租约。
  - 先做 `rediscachex`；`gormcachex` 视需要跟进（租约列或租约表，加条件更新）。
  - 延迟双删只能缩小窗口，进程退出就失效，不做进库里。

### 1.2 用 Redis Pub/Sub 广播失效（可选）

- **问题：** 一个实例上的写入到达不了其他实例的内存层，它们会一直返回旧值，直到过期。
- **做法：** 写入后在一个频道上发布被改动的 key，订阅的实例删除自己内存层里的这些 key。
- **注意：** 断线期间的消息会丢失，最终仍要靠 TTL 兜底。做成可选功能，默认关闭。

## 2. 小问题

- **数据源不支持批量时，`Get` 会等 `GetMany` 的队列：** `GetMany` 一开始就认领所有未命中的 key，下面各层一次读完，再逐个问数据源。一个并发的 `Get` 碰上还在排队的 key，要等它轮到。v1 在这种情况下逐个认领，避免了等待，但下面的层也只能逐个读。需要时可以只在「数据源不支持批量、且只有一层」时退回逐个认领。
- **同一分片上的并发写比 v1 慢：** 微基准里同一分片的 `Set`/`Del` 约 430ns，v1 是 255ns：锁被占用时 `Lock` 要起一个 goroutine 等待，写入还要为抖动取一次随机数。不同分片的写入比 v1 快。见 [research/2026-10-micro-benchmarks.md](research/2026-10-micro-benchmarks.md)。
- **`cachextest.TestBackend` 只测顺序调用：** 可以补一组并发读写的检查，以及过期条目的处理。

## 3. gormcachex 清理过期行

- **问题：** 表只增不减，过期的行要用户自己删。
- **做法：** 提供一个可选的清理函数或后台任务：按 `expires_at < now` 分小批删除（例如每批 100 行、批间停顿），可配置间隔，随 Close 停止；需要时加监控指标。`expires_at` 列已经有索引。

## 4. 热度统计与预热

- **问题：** 重启后内存层是空的，第一波请求都要回源；也没有办法知道哪些 key 最热。
- **做法：** 先做热度统计（每个 key 的访问次数和最后访问时间，带衰减），在此基础上：
  - 关闭时导出最热的 N 个 key，启动时用 `GetMany` 预热；
  - 按热度区分回源并发：热点 key 并发高、冷 key 并发低，保护数据源不被大量冷 key 的慢查询拖垮。
- **注意：** 都做成可选功能；先加基准测试量化统计本身的开销，再决定是否默认开启。
