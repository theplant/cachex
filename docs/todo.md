# 待办

发现了但这次不解决的问题、设计缺口。做完就从这里删掉。

## 1. 跨实例的回源去重（暂不做，有需求再做）

- **问题：** 每个实例的合并回源只在自己进程内生效。20 个实例同时遇到同一个完全未命中（或已经腐烂）的热点 key，数据源会被问 20 次。
- **为什么暂不做：** 最常见的情况已经覆盖了：共享层有陈旧期时，热点 key 过期走后台刷新，而别的实例持有租约时刷新会跳过数据源，所以只有一个实例去刷新（见 [consistency.md](design/consistency.md#租约lease)）。剩下的只是冷 key、或部署、清空 Redis 之后的同时未命中。去重的代价是未命中要等待（持有者崩溃时要等超时）、等待期间轮询共享层、领租约要和读合成一个原子操作。
- **什么时候做：** 实例有几十个、回源很贵、按 key 统计的回源量确实显示同时冷未命中的问题。先试着给共享层设陈旧期。
- **做法：** 拿不到租约的普通读取不立即回源，等一小段时间（远短于回源超时）再读共享层，超时再自己回源；读和领租约放进同一段 Lua，否则两个实例可能都以为自己该回源。

## 2. go-bus 发版后换成正式版本

- **问题：** go.mod 里的 go-bus 是 PR 分支上的伪版本（`v0.1.3-0.20261012191021-fea608be7176`，qor5/go-bus#36），因为 v0.1.2 要求被撤回的 `go-sqlite3 v2.0.3+incompatible`，会把依赖 cachex 的项目降级（见 [backends.md](design/backends.md#gobuscachex)）。
- **做法：** PR 合并、go-bus 发版后，`go get github.com/qor5/go-bus@<新版本>`，确认 `go list -m github.com/mattn/go-sqlite3` 仍是 v1.14.x，删掉这一条。qor5/x 也有同样的问题（qor5/x#657），cachex 不依赖它，不用跟。

## 3. 热度统计与预热

- **问题：** 重启后内存层是空的，第一波请求都要回源；也没有办法知道哪些 key 最热。
- **做法：** 先做热度统计（每个 key 的访问次数和最后访问时间，带衰减），在此基础上，关闭时导出最热的 N 个 key，启动时用 `GetMany` 预热。
- **注意：** 做成可选功能；先加基准测试量化统计本身的开销，再决定是否默认开启。
