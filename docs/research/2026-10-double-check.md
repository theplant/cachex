# 二次检查的价值

日期：2026-10-09。对应决策：[ADR 0008](../adr/0008-on-demand-double-check.md)。

## 问题

二次检查是在认领回源之后、去上游之前，再读一次本层（见 [design/read-path.md](../design/read-path.md#二次检查)）。它有多大收益、多大成本？原来的默认规则「配置了不存在缓存就开启」合理吗？

## 方法

- 上游每次回源耗时 5ms。
- 后端用内存 map 模拟，**先读数据，再等一段延迟才返回**，模拟远程缓存「服务端很快读完，回复在网络上要走一段时间」。延迟分三档：0、200µs、1ms。
- **开环负载**：每毫秒新发起 20 个 `Get`，持续 400ms，不管前面的请求有没有返回。
- 两个场景：
  - 热点 key：一个 key，每 20ms 过期一次（没有陈旧期，过期即回源）；
  - 冷 key：每个请求都是一个新 key，共 8000 个。
- 每个组合跑 3 次取平均。

## 走过的弯路

前两版实验都显示「开不开二次检查没有区别」，原因都在实验本身：

1. **后端先等延迟、再读数据**：竞态窗口就是「读完数据」到「客户端拿到结果去认领」之间的这段路程，这个模型把它压成了零。
2. **闭环负载**（固定 200 个 goroutine 循环调用）：回源期间所有 goroutine 都在等这次回源，没有新请求进来，自然撞不上窗口。真实流量是开环的。

## 结果

| 场景 | 后端延迟 | Enabled | Auto（按需） | Disabled |
|---|---|---|---|---|
| 热点 key：上游调用次数 | 0 | 18 | 18 | 19 |
| | 200µs | 18 | 18 | 19 |
| | 1ms | 18 | 19 | **30** |
| 热点 key：每次 Get 读后端次数 | 1ms | 1.004 | 1.002 | 1.000 |
| 冷 key：每次 Get 读后端次数 | 1ms | **2.000** | 1.005（另一次运行为 1.004） | 1.000 |

- 竞态窗口约等于「后端读取的响应时间 × 这个 key 的请求速率」。后端在内存里时窗口几乎为零，二次检查没有收益。
- 后端读取 1ms、key 很热时，关闭二次检查会多打约 60% 的上游（30 次对比 18 次）；换句话说，开启后少打约 40%。
- 成本只出现在认领回源的那个请求上：热点 key 上摊到每次 Get 几乎可以忽略；但冷 key 上，**总是开启**的话，每次未命中都要多读一次后端（2.000）。
- 按需二次检查（只在「读取之后本 Client 往这个 key 所在的分片写过」时才再读）在热点 key 上拿到了几乎全部收益（19 对比 18），在冷 key 上几乎零成本（1.005 对比 1.000）。多出来的 0.5%，来自和别的 key 共用分片导致的误判。

这是一个合成负载：只有一个热点 key，没有开启返回陈旧值，并在 macOS 上用 `time.Sleep` 模拟延迟。数字的量级可信，具体比例不宜当成定论。
