# 一致性

cachex 在**一个进程**内保证写入顺序。跨进程（多个实例共用 Redis 或数据库）时，打开了租约的共享层不会被旧值回填；其他实例的内存层仍然靠 TTL 兜底。这篇说明边界在哪里、租约怎么工作、TTL 该怎么设，以及以后可以怎么补。

## 单个进程内保证什么

前提：通过**同一个 `Cache`** 调用 `Set`/`Del`，并且先改数据源、再调用它们（见 [write-order.md](write-order.md#使用方式改数据源时要做什么)）。

| 保证 | 靠什么 |
|---|---|
| `Set`/`Del` 返回后，这个进程的读取不会再拿到写入前的值 | 分片锁 + 写入代数（挡住旧值回填）、摘除在途回源（挡住加入更早的回源） |
| 新值不会先于下层出现在上层 | 先写下层、再写上层 |
| 同一个 key 的并发写入，在各层以同一顺序生效 | 同一分片的写入串行执行 |
| 写入失败时，失败的层及其上面不会留下这个 key 的条目 | 失败后从这些层删掉它 |

**不保证**的情况：写入**进行中**，上层落下之前，并发的读取仍可能读到旧值。`Set`/`Del` 一返回，这个窗口就关闭了。

## 多个实例时不保证什么

分片锁和在途回源的登记都在一个 `Cache` 的内存里，其他实例对它们一无所知。

### 1. 其他实例的内存层

```mermaid
sequenceDiagram
    participant A as 实例 A 的内存层
    participant R as 共享的 Redis 层
    participant B as 实例 B
    Note over A: 已缓存 v1
    B->>R: Set(k, v2)（B 自己的内存层也更新）
    Note over A: 仍是 v1，直到它的 TTL 到期
```

实例 B 的写入不会碰实例 A 的内存。A 会一直返回旧值，直到 A 内存层里这个条目腐烂。

**缓解**：内存层的 TTL 不要超过你能接受的旧数据时长。需要更快失效时，在业务代码里广播变更（例如 Redis Pub/Sub），收到消息的实例直接调用自己内存后端的 `Del` 删掉这个 key。

### 2. 旧值回填进共享层

```mermaid
sequenceDiagram
    participant A as 实例 A
    participant R as 共享的 Redis 层
    participant DB as 数据库
    participant B as 实例 B
    A->>R: 未命中
    A->>DB: 读到 v1
    Note over A: 还在返回途中
    B->>DB: 写成 v2
    B->>R: Del(k)
    A->>R: 把 v1 回填 ✗
    Note over R: v1 一直留到 Redis 的 TTL 到期
```

A 的分片锁不知道 B 写过，所以挡不住这次回填。共享层上的 `Cache` 相当于各实例各有一个，它们之间没有协调。这是 cache-aside 模式的经典竞态：

- **概率低**：读和写要在几毫秒内交错；
- **后果持续久**：旧值会存活整个共享层的 TTL。

**解决**：给共享层打开租约（见下文[租约](#租约lease)）。没打开时，共享层的 TTL 也要设成你能接受的旧数据时长。

## TTL 怎么设

这里的 TTL 指每层 `TTL(fresh, stale)` 的总和，也就是条目在这一层最多存活多久。Redis 和 otter 按 `ExpiresAt` 原生过期，不需要另外配置。

| 层 | 建议 |
|---|---|
| 内存层 | 不超过「其他实例可以容忍看到旧值多久」。通常是秒级到分钟级 |
| 共享层（Redis、数据库），打开了租约 | 按命中率需要来设，可以是小时级：旧值回填被租约挡住了 |
| 共享层，没打开租约 | 不超过「旧值回填后可以容忍存活多久」。数据改动频繁、又在意新鲜度时，不宜设成小时级 |

## 租约（lease）

思路和进程内的写入代数相同，只是把「写入发生过」这个事实放到所有实例共享的层里。后端在自己的配置里打开租约（默认关闭），核心包通过 `Leasing` 接口认出它，决策过程见 [ADR 0020](../adr/0020-leases-on-shared-layers.md)。

```mermaid
sequenceDiagram
    participant A as 实例 A
    participant R as 共享层
    participant B as 实例 B
    A->>R: 读 k：未命中
    A->>R: 领租约，得到令牌 t1
    A->>A: 读下层、问数据源，读到 v1
    B->>R: Set/Del k（顺带结束 k 的租约）
    A->>R: PutLeased：k 的租约仍是 t1 才写入 v1
    R-->>A: 令牌已作废，什么也不写 ✓
```

- **什么时候领**：一层未命中之后、往下读之前。第一层在二次检查之后领，下面的层在它未命中之后领。命中不领，所以命中路径不多一次往返。
- **读和领租约不必是原子的**：只要先领租约、再读下层和数据源，之后发生的写入都会让令牌作废；读和领之间插进一次写入，代价只是多回源一次，不会写进旧值。
- **写入作废租约**：开了租约的后端，`Set`、`SetMany`、`Del`、`DelMany` 都结束这个 key 的租约。
- **回填**：只写还持有令牌的层，写完结束租约；回答是「不存在」而这一层不记录它时，带着令牌删除。没拿到令牌的层不回填，它上面不开租约的层照常回填：进程内的层有分片锁保护。
- **释放**：回源失败，或者被这个进程的写入跳过了回填，一次回源结束时把剩下的令牌一起释放，别人不用等它过期。
- **有效期**：`WithFetchTimeout`。持有者崩溃，租约自己过期。
- **别的实例持有租约时**：普通读取照样回源、返回结果，只是不回填那一层；后台刷新跳过数据源，交给持有者，下一次陈旧命中会再试。
- **多个共享层**：各自领租约，各自校验自己那一层的回填。

同一个进程里，读到的值不会倒退：回填不用更旧的答案覆盖更新的，同一个 key 同时只问一次数据源（见 [write-order.md](write-order.md#回填之间旧答案不盖新答案)）。其他实例的写入经共享层到达这个实例的内存层时，没有这个顺序保证。

租约只挡住旧值回填。其他实例的内存层看不到写入，仍然只靠内存层的 TTL（或者以后的失效广播）。但旧值回填影响所有实例、活整个共享层的 TTL，挡住它以后，能看到旧值的最长时间只剩内存层的 TTL。

在 Redis Cluster 上，租约 key 要和数据 key 落在同一个 slot，所以 `Cache` 拒绝含 `}` 却没有 hash tag 的 key（`ErrUnsupportedKey`），见 [ADR 0019](../adr/0019-core-rejects-keys-without-a-redis-slot-for-their-lease.md)。

### 失效广播

写入后在一个频道上发布被改动的 key，其他实例收到后删除自己内存层里的这些 key。断线期间的消息会丢，所以 TTL 仍然是最后的兜底。
